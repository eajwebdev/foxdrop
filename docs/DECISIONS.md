# Decisions

Choices made where MASTER_PROMPT.md was not specific, or where reality forced a change. Newest last.
Format: **what** — why — revisit when.

## Phase 0 (2026-11-25)

1. **Toolchain: AGP 9.3.3, Gradle 9.7.1, Kotlin 2.4.21, KSP 2.3.14.** AGP 9.5.2 is newer, but the Kotlin
   compatibility table (kotlinlang.org) lists AGP ≤ 9.3.x and Gradle ≤ 9.7.x for KGP 2.4.20–2.4.21. We use the newest
   combination both sides officially support. AGP 9 "built-in Kotlin" is used (no `kotlin-android` plugin); KGP comes
   from the build-logic classpath. — Revisit when a Kotlin release lists AGP 9.5+.
2. **compileSdk / targetSdk 37 (Android 17).** Current AndroidX, Compose and OkHttp 5 releases require compileSdk 37;
   §3 asks for the latest stable. minSdk stays 26.
3. **Compose BOM 2026.09.00 (Compose 1.12.1, Material 3 1.4.0), not 2026.11.01.** BOM 2026.11.01 (Compose 1.13)
   requires compileSdk **37.1**, which is beyond the AGP 9.3 line we are on (decision 1). — Revisit with decision 1.
4. **Robolectric runs JVM UI/screenshot tests on API 36** (`core/testing/src/main/resources/robolectric.properties`).
   On the API 37 runtime androidx.test (Espresso) calls `InputManager.getInstance()`, which no longer exists. Apps
   still compile and target 37. — Revisit when androidx.test supports API 37 in Robolectric.
5. **Screenshot helper uses `runAndroidComposeUiTest` (v2).** Roborazzi's standalone `captureRoboImage {}` does not
   pause infinite animations, so a loading spinner made a test redraw forever. The Compose test environment pauses
   them.
6. **Poppins is bundled as font resources (SIL OFL)**, not a downloadable font. Text then looks the same with no
   signal (provinces) and in screenshot tests. ~1.1 MB. Licence: `core/designsystem/licenses/Poppins-OFL.txt`.
7. **Brand pink `#F2014F` stays the primary colour.** White text on it is 4.3:1, so filled pink buttons use 18 sp
   bold labels (WCAG "large text", needs 3:1) and small text links use navy. In dark mode primary is a lighter pink
   (`#FF5C8A`) with dark text (5.8:1).
8. **App icons:** customer = swift-fox mark recoloured white/pink on navy; rider = round badge on navy; business =
   original FD emblem on **white** (recolouring the emblem for navy loses the parcel). Generated by
   `tools/assets/make_assets.py` from `reference/logos/` (never edited).
9. **Splash icon is an Animated Vector Drawable traced from the logo** with vtracer (12 paths). The fox dashes in
   with an overshoot (700 ms). The "parcel drops" part of §11A.1 needs a designer-made vector with the parcel as its
   own layer; the trace cannot separate it. Tracked as `TODO(design-lottie)` together with the intro Lottie.
10. **Modules created only when they have content.** Phase 0 has `core:{model, common, domain, datastore, network,
    data, designsystem, testing}` and `feature:{onboarding, auth}`. `core:database`, `core:location`,
    `core:notifications`, `core:payments`, `core:media` and the other features arrive in the phase that needs them.
11. **Detekt and Spotless run once from the root project** (`foxdrop.quality`) over every module's sources, rather
    than per module. This keeps them independent of AGP 9's new variant API. detekt 1.23.8 is the newest stable
    (2.0 is alpha); its own classpath is pinned to Kotlin 2.0.21.
12. **Feature → feature dependencies fail at configuration time** (in `foxdrop.android.feature`), with a message that
    names both modules. Verified by adding `:feature:auth` to `:feature:onboarding` (build fails).
13. **Supabase session storage:** a custom supabase-kt `SessionManager` (`EncryptedSessionManager`) stores the session
    in `SecureStore` = DataStore + Tink AES-256-GCM, keyset wrapped by an Android Keystore key. supabase-kt's default
    stores it in plain SharedPreferences, which §17 does not allow.
14. **No backend configured ⇒ the app still runs.** Without `SUPABASE_URL`/`SUPABASE_ANON_KEY` in `local.properties`,
    auth calls return `DomainError.NotConfigured` and the UI says the app is not connected yet.
15. **Debug builds allow plain HTTP only to `10.0.2.2`, `localhost`, `127.0.0.1`** (local Supabase). Release builds:
    HTTPS only, system CAs only. Certificate pinning (§17) needs the production domain → Phase 7.
16. **Nothing is backed up** (`allowBackup=false`, data-extraction rules exclude every domain). Users sign in again
    after restoring a phone.
17. **Phone input** strips a leading `0` or `63`, because the field already shows `+63` and people type `0917…`.
    (Found by a unit test, confirmed on the emulator.)
18. **Auth in Phase 0 is wired to Supabase but not verified end to end** (no Docker on this PC → no local stack).
    Google sign-in shows "coming soon"; Credential Manager + SMS User Consent come in Phase 1.
19. **Supabase CLI 3.4 writes `supabase/config.jsonc`** (new format; older docs mention `config.toml`). Local phone
    auth uses fixed test OTPs (`123456`) for the demo numbers `+63 917 000 0001…0005`; no SMS is sent locally.
20. **Super Admin has no Android screens**; the business app is store + operator only (MASTER_PROMPT §2, §4).
21. **Windows owner machine:** Gradle runs on Android Studio's bundled JBR 21 (`JAVA_HOME` = `…\Android Studio\jbr`).
    Helper scripts are Python/Gradle, not bash.
22. **CI uses JDK 21 (Temurin)** to match the local JBR 21. Roborazzi compares with a 1 % threshold; Linux vs Windows
    rendering may still differ slightly — if CI reports diffs, re-record baselines on CI and commit them.
23. **Flat cards (owner request, 2026-11-25):** no shadows or tonal elevation anywhere; cards use `FoxCard` — a soft
    rounded 1 dp `outlineVariant` border on `surface`. The `FoxElevation` tokens were removed. Added to MASTER_PROMPT
    §11.
24. **Google button shows the official four-colour "G"** (`feature/auth/.../ic_google_logo.xml`), untinted, left of
    "Continue with Google" (owner request; Google Sign-In branding guidelines). Facebook (feature flag, §3) will
    follow the same rule.
25. **Test OTPs are local-only.** `supabase/config.jsonc` `auth.sms.test_otp` (`+63 917 000 0001…0005` → `123456`) is for the
    local stack. **Never run `supabase config push` with this file against the hosted project**; Phase 1 moves these
    codes to a local-only override before a hosted project is linked. (From the Phase 0 security review.)

## Before Phase 1 (2026-11-25)

26. **Database stays Supabase Postgres; hosting is Hostinger for the admin web only.** The owner considered MySQL
    because of Hostinger hosting. Decision: keep Supabase (RLS province isolation, Auth, Realtime, Storage, Edge
    Functions are required by §3/§17 and would otherwise have to be hand-built). Hostinger (VPS preferred) hosts
    `admin-web`, which connects to the Supabase Postgres; Hostinger's MySQL is not used. MASTER_PROMPT §20.6 updated.

## Phase 1 (2026-11-25)

27. **`user_roles` replaces `store_staff`.** One table holds every grant (`role`, `province_id`, `store_id`), with a
    check that each role carries the right scope. RLS helpers (`private.has_role`, `operator_province_ids`,
    `member_store_ids`) read this table, not JWT claims, so a revoked role stops working at once. The `app_roles`
    JWT claim (access-token hook) is only for UI hints and the admin web.
28. **Published storefronts are public by design.** `anon` can read enabled provinces, published stores, their
    categories/products, current rate cards and reviews (browse before sign-in, §9.1). Everything else needs a session.
29. **PSGC province list** comes from the psgc.cloud mirror of the PSA PSGC file (82 provinces + NCR as one
    service area, 83 rows). Codes are the 10-digit PSGC codes.
30. **Append-only tables keep no FK to `auth.users` on actor columns** (`audit_logs.actor_user_id`,
    `order_events.actor_user_id`, `ledger_txns.created_by`, `delivery_rate_cards.created_by`). An `on delete set null`
    FK would have to UPDATE those rows, which the append-only triggers reject, so deleting a user would fail. The
    history outlives the account; the id stays as a plain uuid. (Phase 1 code review.)
31. **`ticket_messages.province_id` is copied from the ticket by a trigger**, never trusted from the client, so every
    provincial row has `province_id` (CLAUDE.md) without a second source of truth.
32. **Test OTPs stay in `supabase/config.jsonc`** for the 9 phone demo accounts (the admin has none; it signs in to the
    web with email + password). The Supabase CLI has no local-only override file, so DECISIONS 25 is kept as a rule:
    the hosted project's auth settings are managed in the dashboard and **`supabase config push` is never run**. This is
    also on the pre-launch checklist (§19 Phase 7).
33. **Google sign-in** uses Credential Manager (`GetSignInWithGoogleOption`) with a SHA-256 nonce, then
    `signInWith(IDToken)`. It is enabled only when `GOOGLE_WEB_CLIENT_ID` is set in `local.properties`; otherwise the
    button explains that Google sign-in is not set up yet. OTP autofill uses the SMS User Consent API (no SMS
    permission).
34. **Role routing reads the `app_roles` JWT claim from the stored session** (no request, works offline in all three
    apps). Admin accounts are kept out of every Android app ("use the web dashboard"); in the business app an
    operator role wins over a store role; grants come oldest first. A role change shows after the next token refresh
    (≤ 1 token lifetime) — flows that grant a role (Phase 2 approvals, Phase 4 rider approval) refresh the session.
    RLS, which reads `user_roles` directly, decides every read, so a stale claim never exposes data. No session →
    sign out. (Phase 1 /simplify: replaced a second, network-only roles query.)
35. **Auth redirects** use one scheme per app (`foxdrop-customer://auth`, `foxdrop-rider://auth`,
    `foxdrop-business://auth`). The launch intent is handled only on a fresh launch (not after process death or from
    Recents) and its data is cleared, so a one-time code is never exchanged twice. Supabase Auth uses the **PKCE**
    flow: the implicit default would import any tokens in a crafted `foxdrop-<app>://auth#access_token=…` link and
    silently sign the victim into an attacker's account (Phase 1 security review). Verified App Links (`https://`)
    replace the custom schemes once the production domain exists (Phase 7).

## Phase 1b — backend moved to Laravel (2026-11-26)

36. **The backend is Laravel 13 + PostgreSQL 17 + PostGIS in `backend/`, replacing Supabase** (owner decision,
    2026-11-26: own hosting on a Hostinger VPS, one backend for apps and admin web). Supersedes 26 (and the Supabase
    parts of 19, 25, 27, 32–35). The Phase 1 schema was ported, not redesigned: `backend/database/schema/*.sql` run
    by Laravel migrations keep every database rule (checks, append-only ledger + zero-sum check, one live license per
    province, composite province FKs). Supabase-only parts were dropped: `auth.users` (now Laravel `users`), RLS,
    grants, Vault, Storage policies, the access-token hook. `supabase/` was deleted.
37. **Local tools are portable, in `D:\devtools`** (PHP 8.4, PostgreSQL 17 binaries + PostGIS bundle; no Docker, no
    admin rights; drive C: had 2.8 GB free). XAMPP's PHP 8.2 is untouched (Laravel 13 needs 8.3+). The PostGIS
    bundle overwrites PostgreSQL's `libcurl.dll` with one that needs DLLs it does not ship, so PostgreSQL's own copies
    are restored (`docs/DEVELOPMENT.md`).
38. **Province isolation is enforced in Laravel**: `visibleTo(User)` query scopes on every provincial model, used by
    every controller that lists or shows provincial rows (from Phase 2), plus policies for writes. Pest feature tests
    on real PostgreSQL prove isolation (ported from the pgTAP suite). The database still guarantees the invariants
    that must hold whatever code path writes.
39. **Sign-in tokens are Sanctum personal access tokens**, one per device, named after the device, valid 90 days
    (`FOXDROP_TOKEN_TTL_MINUTES`). Suspended accounts are refused at sign-in and on every API call.
40. **Phone OTP is our own service**: 6 digits, only an HMAC (app key) stored, 5-minute expiry, 5 attempts, one use,
    a new code retires older ones, 60 s between sends (the app's countdown matches), rate limits per phone and per
    IP. Demo numbers have fixed codes via `FOXDROP_TEST_OTPS`, honoured only in `local`/`testing`; production
    refuses to boot with fixed codes or the `log` SMS driver.
41. **Google sign-in is verified by the backend** (Google's JWKS, issuer, audience = our client IDs, expiry, nonce =
    SHA-256 of the app's raw nonce). Linking: by Google subject first, then by Google-verified email. Linking to an
    account whose email was never verified removes its password and signs out its devices (blocks pre-account
    takeover by someone who registered the victim's email first).
42. **Role routing reads `/me` when online and the copy saved at sign-in when offline** (supersedes 34's JWT claim).
    A `401` from any call clears the session once in `FoxApiClient`, and the session observers send the user to
    sign-in (the global session-expiry handler planned in the Phase 1 report).
43. **No deep-link auth redirects** (supersedes 35): nothing signs in through a browser any more, so the per-app
    `foxdrop-<app>://auth` intent filters and their handler were removed.
44. **PostgreSQL sessions use UTC** (`config/database.php` `timezone`). Laravel writes timestamps without an offset; a
    Manila-time session read them 8 hours off (found by the OTP expiry tests). Manila time is for display only.
45. **License numbers are encrypted by Laravel** (`encrypted` cast, app key) instead of pgcrypto + Vault. A separate
    rotation-safe key (`APP_PREVIOUS_KEYS`) is part of the Phase 7 runbook.
46. **Email sign-up signs in right away**; email verification arrives with the email features (Phase 6). Google
    accounts are created with a verified email.
47. **The admin web lives inside `backend/`** (Inertia + React in `resources/js`, Phase W1), not in a separate
    `admin-web/` app. The old `admin_web` database role, `admin_api.*` SQL functions and `admin` schema rules no longer
    apply: admin actions are Laravel Actions with policies and audit-log rows.
48. **Sign-in rate limits are tight per phone / email and loose per IP** (Phase 1b code review): Philippine carriers
    put many subscribers behind one IP (CGNAT), so per-IP limits only stop bulk abuse. Behind the VPS proxy the
    client IP comes from `X-Forwarded-For`, trusted only for `TRUSTED_PROXIES`. It is read in `bootstrap/app.php`, so on the
    VPS it must be a real environment variable (systemd/php-fpm), not only a `.env` line, once `config:cache` runs.
49. **Google sign-in hardening** (Phase 1b code review): an email already linked to one Google account is never moved
    to another (409); each Google ID token is accepted once (its nonce is remembered until it expires); an unknown
    signing key triggers one refetch of Google's keys; Google being unreachable answers 503, not "invalid".
50. **The schema files were corrected in place** (ledger entries must carry their wallet's province; favourites and
    reviews tie to their store / product / rider province). Allowed only because no database outside development
    exists yet; from the first deploy on, schema files are forward-only.
51. **Routing uses the saved roles first, then the server's** (Phase 1b /simplify; refines 42): the app opens straight
    to its home from the roles saved with the session (no wait on a slow provincial network), then `/me` updates
    them and re-routes only if they lead elsewhere; a rejected session still signs out.
52. **Province isolation stays an explicit `visibleTo($user)` scope** (one `VisibleToViewer` trait holds the admin
    bypass; each model states only its rule). A global scope was considered and rejected for now: queues, the
    scheduler and admin actions have no request user, and a deny-by-default global scope would make every job opt
    out. From Phase 2 every endpoint that reads provincial rows gets a Pest test proving another province sees 0 rows.
53. **The 60-second OTP resend wait is a rate limit** (`otp-send`, per phone, with the remaining seconds in the 429
    body), not a database query; the app's countdown uses the same 60 s. Rate limits and the Google nonce use the
    cache store: `database` locally, **Redis on the VPS** (§20.6).
54. **Sanctum does not track `last_used_at`** (it would write the token row on every API call); expired tokens and
    old OTP codes are pruned daily by the scheduler.

## Phase 2 (2026-11-26)

55. **License flow: apply → admin approves → pay → ACTIVE.** Applying creates the license as `APPLIED` (the unique
    index then blocks the province for others); an admin approval moves it to `PENDING_PAYMENT`; payment activates it
    for 365 days and grants the operator role. Until the admin web (Phase W1) the admin step is the Artisan command
    `foxdrop:operator-application approve|reject <id>`, running the same Action the web will call.
56. **Renewal extends the same license** (`end_at = max(now, end_at) + 365 days`) instead of a new row, because the
    one-live-license index forbids a second live row; each term is a `payments` row. `renewal_of` stays unused.
57. **Payments go through a `PaymentProvider`**: `paymongo` (Checkout Sessions API; secret key and webhook secret in
    `backend/.env`) and `fake` (local/testing only: `/dev/checkout/{payment}` web page with Pay/Cancel that runs the
    same success handler as the webhook). Production refuses to boot with the fake driver. This lets the whole flow
    run on the emulator before the owner has PayMongo keys.
58. **Zones are circles in the apps for now** (centre = province centre or the operator's current location, radius
    0.5–30 km, stored as a PostGIS polygon). The API also accepts polygons; the drawn-polygon map editor comes with
    Google Maps in Phase 3 (needs `MAPS_API_KEY`).
59. **An approved store goes straight to `ACTIVE`** (visible to customers); `APPROVED` is skipped because nothing
    happens between the two in v1. A rejected store is `REJECTED` (new enum value) with a reason and can be
    resubmitted.
60. **Partner documents** live on a private disk, images only (≤ 8 MB), re-encoded by the server (drops EXIF/GPS),
    and are shown to reviewers through 10-minute signed URLs (no bearer header needed by the image loader).
61. **Rider registration is one multipart request** (details + all photos), matching the single Submit button in
    `04_Rider_Workflow.png`; documents are reviewed as a set.
62. **Feature modules for Phase 2**: `operator-license`, `operator-zones-rates`, `operator-partners` (store + rider
    approvals in one module: same list/detail/approve pattern), `store-onboarding`, `rider-onboarding`, plus core
    `payments`, `media`, `location`. Other §4 names arrive with their phases.
63. **Applicants learn about approvals by checking status** (status screens refresh on open, pull and a button);
    push notifications arrive with FCM in Phase 3/6.
64. **"Not registered" business and rider accounts get onboarding homes** instead of the mismatch screen: they are
    now `HomeDecision.Home` cases (`BusinessOnboarding`, `RiderOnboarding`). Admin accounts still get the mismatch
    screen.
65. **An operator role counts only while its province's current license is theirs** (Phase 2 code review): when a
    license expires and the province is licensed to someone else, the former operator keeps the role row (history)
    but no longer reaches the province. Reviews, zones, rates and the store fee all need that license ACTIVE or in
    GRACE; platform admins may review anywhere.
66. **Phase 2 models have no factories yet** (Payment, OperatorApplication, DeliveryZone, DeliveryRateCard,
    StoreDocument, RiderDocument, WebhookEvent): their tests create rows through the very Actions under test, which
    is what the app does. Factories are added when a test needs such a row without its Action.
67. **Deferred Phase 2 refactors** (from /simplify; working and end-to-end tested as they are): move the payment flow
    (models, poller, start → checkout → poll) into `core:payments` when the second payment type arrives (store top-up,
    Phase 5); replace the role-refresh plumbing through the NavHosts with `RoleRepository.refresh()`; a shared
    onboarding ViewModel helper and one photo-slot model for the three application flows; `LoadableContent` in the
    three onboarding screens; cursor pagination for the review lists (Phase 6, when lists grow).
68. **Partner document photos are never cached on disk** on the reviewer's phone (memory only), as personal data
    under the Data Privacy Act.
